# Архитектура модульной версии

## Цель

Разделить исходный монолит `src/spred.cpp` (6 964 строки) на независимо компилируемые модули, не подменяя торговую стратегию новой. Основной код находится в `src/`, его объявления и модели — в `include/spred/`. Исполняемый файл по-прежнему называется `spred`.

## Границы ответственности

| Каталог | Ответственность |
|---|---|
| `app/` | Запуск, чтение параметров, жизненный цикл сессии, replay и маршрутизация событий |
| `core/` | `MM_*`, время, логирование, обработчик сигнала, кодирование, HMAC и лимиты запросов |
| `net/` | TLS, HTTP, WebSocket; транспорт без выбора торговых решений |
| `exchange/` | Метаданные символов и REST-операции MEXC |
| `protocol/` | Преобразование protobuf-данных MEXC в типизированные сообщения |
| `market/` | Книга заявок, VWAP, модель потока сделок и отложенных событий |
| `feeds/` | Внешняя fair-price лента Bybit и её состояние |
| `trading/strategy.cpp` | Торговые решения для одного символа |
| `trading/paper.cpp` | Бумажные ордера, очередь, задержки, симуляция исполнений |
| `trading/live_executor.cpp` | Синхронизация и исполнение реальных ордеров |
| `trading/live_ledger.cpp` | Учёт реальных исполнений, комиссий и markout |
| `reporting/` | Периодические строки и итоговые отчёты |

`src/main.cpp` только вызывает `spred::runApplication`. Объявления классов отделены от тел методов: HTTP/WebSocket, REST, paper и live собираются в отдельные объектные файлы. Небольшие структуры и короткие методы оставлены в заголовках намеренно.

## Поток данных

```
WebSocket / replay
  -> protocol::MEXC decoding (namespace spred)
  -> app: события и их упорядочивание
  -> SymCtx: книга + поток + paper + live-состояние одного символа
  -> trading: tickSymbol
  -> paper / live executor
  -> reporting
```

Названия каталогов обозначают модули. Основное пространство имён — `spred`, существующие вспомогательные пространства — `spred::ws` и `spred::pb`.

## Состояние и зависимости

- Состояние символа сосредоточено в `SymCtx`, описанном в `app/symbol_context.hpp`.
- `SessionOptions` передаёт извлечённым функциям контекст, ранее неявно захватывавшийся большими лямбдами `main`: live-конфигурацию, счётчики, часы и параметры сессии. Ссылки действительны только в течение `runApplication`.
- Общие часы replay, сигнал остановки, IP-лимитер и состояние fair-price имеют одно определение в `.cpp` и объявления `extern` в соответствующем заголовке. Разделение файлов не должно создавать отдельный лимитер или часы на каждый модуль.
- Реализации скрыты в `.cpp`; локальные помощники остаются `static`. Только небольшие функции заголовков — `inline`.
- `platform.hpp` пока объединяет POSIX/OpenSSL и стандартные заголовки исходного проекта. Это компромисс миграции, не минимальная система зависимостей.

## Сборка и проверки

На Ubuntu/Debian или внутри WSL2:

```bash
sudo apt-get update
sudo apt-get install -y g++ make libssl-dev python3
make -j2
make check
```

`make` собирает 22 единицы компиляции и использует `.d`-файлы для зависимостей от заголовков. Повторная сборка изменённого модуля не требует ручного перечисления всех исходников. Артефакты находятся в `build/`, бинарник — `./spred`; `make clean` удаляет их.

`make check` использует стандартную библиотеку Python, GCC и тестовую Linux-библиотеку запрета сетевых соединений. В тестах нет настоящих ключей, подтверждения live-торговли или отправки заявок. Реальный replay вне тестов сохраняет поведение исходника и может запрашивать метаданные символа; только тестовый стенд заменяет ответ на локальную заглушку.

## Что сохранено

- Имя бинарника, позиционные аргументы, переменные `MM_*` и их значения по умолчанию.
- Торговые формулы, проверки live-режима, последовательность обработки событий и формат raw-replay.
- Форматы отчётов, предназначенные для существующих Python/Bash-инструментов.
- Python-утилиты, скрипты экспериментов и исследовательские результаты. Их поведение не переписывалось.
- История и описание параметров из шапки монолита перенесены в `LEGACY_CONFIGURATION_AND_HISTORY.md`.

## Оставшийся технический долг

Это первая структурная переработка, а не полная новая архитектура. Оркестратор сессии и стратегия всё ещё крупные; общие `g_*`, detached-поток fair-price, собственные JSON/protobuf-парсеры и сетевой стек сохранены. Следующий отдельный этап — явное владение ресурсами и жизненным циклом потоков, инъекция транспорта и часов, более узкие интерфейсы стратегии и расширенные тесты отказов live API. Такие изменения требуют отдельной проверки и не должны смешиваться с переносом методов по файлам.

Модульность и успешные офлайн-тесты не подтверждают прибыльность, полную корректность исполнения или готовность live-режима к реальным средствам.
